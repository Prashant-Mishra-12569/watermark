# Watermark

*Real people leave a mark.*

> Watermark lets an app accept only wallets backed by a real bank card. A user taps the card on our Android app
> once, a zero-knowledge proof is checked on-chain, and the wallet gets a "stamp". Your contract, backend or AI agent
> checks the stamp before it lets a wallet in: airdrops, mints, sponsored gas, faucets, rewards, votes or AI agent
> payouts. Bots can make wallets for free, but they can't make bank cards.

This file is the full reference for people and for AI agents. The same text is at /llms.txt.
- Website: https://usewatermark.xyz
- Source code (MIT licence): https://github.com/Prashant-Mishra-12569/watermark
- Status: built at ETHGlobal Mumbai 2026. Test networks only. Every address and app id below comes from
  deployments/whitechain.json and deployments/devnet.json in the repo.

## 1. What Watermark is

- A stamp on (wallet, appId) means: this wallet was linked to one real bank card that passed this app's card filter.
- It is not identity, KYC, age, balance or one-person-one-vote. A person with three cards can get three stamps.
- It makes every extra wallet cost a real bank card. That is what stops bots from farming airdrops and rewards,
  draining sponsored gas and faucets, and faking crowds in votes.
- The card number is never stored and never goes on-chain. Our prover holds the card data in memory only while it
  proves, then wipes it. One card can stamp one wallet per app. A stamp lasts up to 3 months.
- Checking a stamp is one on-chain read: no API key, no account with us, no server of ours in the path.

## 2. How it works

### The user
1. Opens your app's verify link: https://usewatermark.xyz/verify?app=<APP_ID>
2. Picks a wallet: their own browser wallet (for example MetaMask) or one the page makes in the browser. The stamp
   goes to that wallet, so it should be the wallet they will claim with.
3. Scans the QR code with an Android phone running Watermark Tap, our NFC app. The phone shows the wallet's last 4
   characters, so the user can check they match the page.
4. Taps a bank card on the phone. The chip signs a fresh challenge derived from the session. No payment is made and
   nothing is sent to a bank.
5. The page shows "Verified" once the stamp is on-chain. The user pays no gas and needs no WBT.

### Your app
1. Picks an appId: our live app for real RuPay cards, or its own app with its own card list (section 10).
2. Checks isStamped(wallet, appId) before it pays out: in Solidity (section 4), with the TypeScript SDK (section 5),
   or from an AI agent over MCP (section 6).
3. Sends wallets without a stamp to the verify link (section 8).

### The relayer (https://api.usewatermark.xyz)
1. Signs a session for the wallet and appId (EIP-712, valid for 10 minutes). This is off-chain, so it costs no gas.
2. Receives the proof from the prover, simulates the stamp transaction, and sends it only if the simulation passes.
   The relayer pays the gas.
3. Relays gas-free USDT payments for stamped wallets through WatermarkSponsor (section 9), and mints the Genesis Pass.
4. Refuses unstamped wallets and wallets over their daily quota, and stops at its per-transaction gas caps and daily
   budget caps.

### The prover (https://prover.usewatermark.xyz)
1. Receives the card data from the phone, encrypted (RSA-OAEP + AES-GCM, bound to the session). The phone has already
   checked the certificate chain and the app's filter itself.
2. Decrypts it in memory and builds a zero-knowledge proof (Noir, UltraHonk) that a genuine network-signed card, which
   passes this app's filter, signed this session's challenge.
3. Computes a nullifier from the card's key, so one card can stamp only one wallet per app.
4. Sends the proof to the relayer and drops the card data. Nothing is written to disk.

Then WatermarkRegistry verifies the proof on Whitechain Sepolia and records the stamp: wallet, appId, nullifier and
expiry. Any contract or client can read it with isStamped(wallet, appId).

## 4. Integrate in Solidity

This works for contracts on Whitechain Sepolia (chain 1874), where the registry is. A contract on another chain can't
read the registry: check in your backend instead (section 5), or build your allowlist with checkMany.

Any contract can check a stamp in one call (from docs/INTEGRATE.md):

```solidity
interface IWatermarkRegistry {
    function isStamped(address wallet, uint256 appId) external view returns (bool ok, uint64 expiresAt);
}

modifier onlyStamped() {
    (bool ok, uint64 expiresAt) = watermark.isStamped(msg.sender, watermarkAppId);
    require(ok && expiresAt > block.timestamp, "Watermark: no live stamp");
    _;
}
```

The full contract, as the MCP tool watermark_integration_snippet returns it for the live app (gate + one claim per
wallet):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.30;

interface IWatermarkRegistry {
    function isStamped(address wallet, uint256 appId) external view returns (bool ok, uint64 expiresAt);
}

/// Gate a function to wallets with a live Watermark stamp for one app.
/// A stamp = one real bank card that passed the app's filter. Not identity or KYC.
abstract contract WatermarkGated {
    // WatermarkRegistry on whitechain: 0x998934Efa31a6bE75945fDfAa126d3D6401F8Fd6
    IWatermarkRegistry public immutable watermark;
    uint256 public immutable watermarkAppId;

    constructor(IWatermarkRegistry registry) {
        watermark = registry;
        watermarkAppId = 393344891601835728760966937624776276735512086066329273346256164761263100630;
    }

    modifier onlyStamped() {
        (bool ok, uint64 expiresAt) = watermark.isStamped(msg.sender, watermarkAppId);
        require(ok && expiresAt > block.timestamp, "Watermark: no live stamp");
        _;
    }
}

// Example: one claim per stamped wallet
contract Drop is WatermarkGated {
    mapping(address => bool) public claimed;
    constructor(IWatermarkRegistry r) WatermarkGated(r) {}
    function claim() external onlyStamped {
        require(!claimed[msg.sender], "already claimed");
        claimed[msg.sender] = true;
        // ... send the reward
    }
}
```

Notes
- Deploy it with the registry address 0x998934Efa31a6bE75945fDfAa126d3D6401F8Fd6 as the constructor argument.
- isStamped returns (ok, expiresAt). `ok` already includes the expiry; the `expiresAt > block.timestamp` test is a
  second guard. expiresAt is unix seconds, 0 if the wallet was never stamped.
- The registry makes sure one card stamps only one wallet per app. "One claim per wallet" is your contract's job (the
  `claimed` mapping above).
- The gate checks msg.sender. If a claim goes through a router or a relayer, check the wallet that receives the reward.
- To test it, use a small mock registry that returns (false, 0) for an unstamped wallet (section 13 has one).

## 5. Integrate with the TypeScript SDK

Install: @watermark/sdk lives in the repo (sdk/) and is not on npm yet. Either use it from a clone of the repo (pnpm
workspace, Node 24), or use the plain viem read further down, which gives the same answer as check().

From docs/INTEGRATE.md:

```ts
import { check, checkMany } from "@watermark/sdk";

const registry = "0x998934Efa31a6bE75945fDfAa126d3D6401F8Fd6";
const appId = "393344891601835728760966937624776276735512086066329273346256164761263100630";

const { stamped, expiresAt } = await check(userAddress, appId, { registry });
if (!stamped) showGetStampedButton(); // links to the /verify page (verifyLink)

// Airdrop or allowlist export: up to 200 wallets per call, one multicall
const results = await checkMany(addresses, appId, { registry });
```

It reads the chain directly, with no API key and no relayer. It works in the browser. Node apps can use
`@watermark/sdk/node`, which reads the addresses from deployments/.

### What the SDK exports (sdk/src)
Main entry, browser-safe (`@watermark/sdk`):
- check(wallet, appId, opts) -> { stamped, expiresAt }. opts: { registry, chain?: "whitechain" | "devnet", rpcUrl?,
  client?, now? }. expiresAt is unix seconds, 0 = never stamped. Throws on a malformed wallet or appId.
- checkMany(wallets, appId, opts) -> { [checksummedWallet]: { stamped, expiresAt } }. At most 200 wallets, one
  multicall on Whitechain. A failed read counts as not stamped.
- verifyLink(appId, wallet | null, siteUrl, chain?) -> "https://usewatermark.xyz/verify?app=<appId>". The wallet is
  only validated, never put in the link: the page never takes a wallet from the URL.
- appInfo(appId, { registry }) -> { appId, exists, owner, rulesRoot, sessionSigner }
- stampHistory(appId, { registry, fromBlock }) -> { total, uniqueWallets, active, checked, stamps[] }. Reads Stamped
  events from the deploy block (12335610) in chunks; use the official RPC for logs.
- prepareRegisterApp({ owner, salt, rulesRoot, sessionSigner, registry }) -> { tx, appId, warnings }. tx is UNSIGNED:
  { to, data, value: "0", chainId }. The SDK never signs or sends anything.
- computeAppId(owner, salt) = uint256(keccak256(abi.encode(owner, salt))) >> 8
- draftPolicy(input), explainPolicy(policy), supportedCards()
- whitechainSepolia, altmempoolDevnet (viem chains), USDT_WHITECHAIN, WATERMARK_REGISTRY_ABI, MAX_CHECK_MANY (200)

Node only (`@watermark/sdk/node`): check, checkMany, appInfo, stampHistory and prepareRegisterApp without passing the
registry (read from deployments/), plus auditApp(appId), getPolicy(appId), listPolicies(), deployedApps(chain),
loadDeployment(chain) and registryFor(chain).

### Without the SDK: plain viem
The same read as check(), with nothing but viem:

```ts
import { createPublicClient, defineChain, http } from "viem";

// Whitechain Sepolia. Define it yourself: viem's built-in `whitechainTestnet` is a different chain (2625).
const whitechainSepolia = defineChain({
  id: 1874,
  name: "Whitechain Sepolia",
  nativeCurrency: { name: "WhiteBIT Coin", symbol: "WBT", decimals: 18 },
  rpcUrls: { default: { http: ["https://rpc.testnet.whitechain.io"] } },
});

const REGISTRY = "0x998934Efa31a6bE75945fDfAa126d3D6401F8Fd6";
const APP_ID = 393344891601835728760966937624776276735512086066329273346256164761263100630n;
const abi = [{
  type: "function", name: "isStamped", stateMutability: "view",
  inputs: [{ name: "wallet", type: "address" }, { name: "appId", type: "uint256" }],
  outputs: [{ name: "ok", type: "bool" }, { name: "expiresAt", type: "uint64" }],
}];

const client = createPublicClient({ chain: whitechainSepolia, transport: http() });

export async function isStamped(wallet) {
  const [ok, expiresAt] = await client.readContract({
    address: REGISTRY, abi, functionName: "isStamped", args: [wallet, APP_ID],
  });
  return ok && Number(expiresAt) > Math.floor(Date.now() / 1000);
}
```

Always check on your server before paying out. Never trust a "stamped" flag sent by the browser.

## 6. Integrate with an AI agent via MCP

The Watermark MCP server (mcp/ in the repo) lets an agent check a wallet before paying a reward or giving access,
audit an app, or draft a card filter.
- It holds no keys and never signs or sends a transaction. Everything it returns is data.
- No tool takes card data. Filter prefixes are 6- or 8-digit BINs from a public BIN list; the schema rejects anything
  longer.
- It runs locally over stdio.

### Install
Clone the repo, run `pnpm install` at the repo root (Node 24 runs the TypeScript directly), then add this to your
client's MCP server config (the exact file depends on the client). From mcp/README.md:

```json
{
  "mcpServers": {
    "watermark": {
      "command": "node",
      "args": ["/absolute/path/to/watermark/mcp/src/index.ts"],
      "env": { "WHITECHAIN_RPC": "https://rpc.ankr.com/whitechain_testnet" }
    }
  }
}
```

Optional environment variables: WHITECHAIN_RPC (reads on Whitechain), ALTMEMPOOL_EXEC_RPC (reads on the devnet),
WATERMARK_LOGS_RPC (event history; defaults to https://rpc.testnet.whitechain.io).

### Tools
Types: wallet = 0x address (40 hex characters); appId = decimal string; chain = "whitechain" (default, Whitechain
Sepolia 1874) or "devnet" (1337); bytes32 = 0x + 64 hex characters. A trailing ? means optional.

1. watermark_check_wallet
   Is this wallet stamped for this app, and until when? Use it before paying a reward or giving access.
   Inputs: wallet, appId, chain? -> returns stamped, expiresAt, expiresAtIso, meaning
2. watermark_check_wallets
   The same check for an airdrop or allowlist, in one multicall.
   Inputs: wallets (1 to 200), appId, chain? -> returns total, stamped (count), results per wallet, meaning
3. watermark_app_info
   An app's on-chain record (owner, rulesRoot, session signer) plus an audit: is the filter enforced on-chain the
   one the app publishes?
   Inputs: appId, chain? -> returns exists, owner, rulesRoot, sessionSigner, audit { matches, published, issues }
4. watermark_stamp_history
   Transparency: total stamps, unique wallets, how many are live now, the latest ones with explorer links.
   Inputs: appId, chain?, limit? (1 to 200, default 20) -> returns totalStamps, uniqueWallets, liveNow, latest[]
5. watermark_list_apps
   The registry address and the deployed apps (test and live) with their filter labels.
   Inputs: chain? -> returns registry, apps[] { appId, environment, label, rulesRoot }
6. watermark_draft_policy
   Turns rules like "SBI RuPay debit only" into filter leaves, their Poseidon2 rulesRoot, warnings, and what a stamp
   reveals. Prefixes come from a public BIN list, never from someone's own card. Signs nothing.
   Inputs: networks (one or more of RUPAY, VISA, MASTERCARD), prefixes (up to 8,192 items of { network, prefix (6 or
   8 digits), bank?, type? (debit | credit | prepaid), status? (tested | listed) }), label? (up to 80 characters),
   environment? (live | test), banks?, types?, quotaPerDay? (1 to 1000), stampMonths? (1 to 3)
   -> returns policy, rulesRoot, warnings, explanation, nextStep
7. watermark_prepare_register_app
   An UNSIGNED registerApp transaction for a company's own app, card filter and session signer, plus the predicted
   appId. The owner reviews it and sends it from their own wallet.
   Inputs: owner (wallet), rulesRoot (bytes32, from watermark_draft_policy), sessionSigner (wallet), salt? (bytes32,
   random if left out), chain?
   -> returns unsignedTransaction { to, data, value, chainId }, salt, appId, warnings, nextStep
8. watermark_create_verify_link
   A link that sends a user to the /verify page for an app.
   Inputs: appId, siteUrl (the Watermark website: https://usewatermark.xyz), chain? -> returns link, howItWorks
   Example: https://usewatermark.xyz/verify?app=393344891601835728760966937624776276735512086066329273346256164761263100630
9. watermark_get_policy
   The committed filter policy for an appId: label, environment, leaves, rulesRoot, quota.
   Inputs: appId -> returns policy, meaning
10. watermark_explain_policy
   Plain language: who passes, what a stamp reveals publicly, and what it does not prove.
   Inputs: appId -> returns label, whoPasses, whatAStampReveals, whatItDoesNotProve, limits
11. watermark_supported_cards
   Which cards can be proven today: RuPay debit is live; Visa and Mastercard are planned, not live.
   Inputs: none -> returns cards[] { network, status, detail }, filters
12. watermark_integration_snippet
   Solidity (the onlyStamped modifier) or TypeScript (check, allowlist export) with the real registry address filled in.
   Inputs: language (solidity | typescript), appId, chain? -> returns language, registry, code

A typical agent rule: "Before sending a reward to a wallet, call watermark_check_wallet with our appId. Pay only if
stamped is true. If it is false, send the user the link from watermark_create_verify_link."

## 7. HTTP API

You don't need the HTTP API to check a stamp: read the chain (sections 4 to 6). These endpoints run the Watermark
pages. JSON everywhere; uint256 values are decimal strings and bytes are 0x-hex. Sessions, stamps, payments, funding
and the pass routes are rate-limited per IP. The relayer accepts browser calls only from the origins it is configured
for (CORS), so call it from a server.

## 8. Letting your users get stamped

### The verify link
  https://usewatermark.xyz/verify?app=<APP_ID>
For the live app:
  https://usewatermark.xyz/verify?app=393344891601835728760966937624776276735512086066329273346256164761263100630
Build it with verifyLink(appId, null, "https://usewatermark.xyz") or watermark_create_verify_link. Label the button
something like "Get verified with Watermark".

The link works for app ids our relayer serves, which includes the live app. Any other appId is refused with
UNKNOWN_APP, so an app with its own card list runs its own session signer (section 10).

### What a user needs
- An Android phone (Android 8 or newer) with NFC, running Watermark Tap. It is not in an app store. Its download page
  is https://usewatermark.xyz/app (an .apk file, once it is posted there). At ETHGlobal Mumbai, users can tap on our
  phone at the Watermark booth.
- A RuPay bank debit card issued in India whose prefix is on the live list (prepaid cards don't count). Visa and
  Mastercard don't work yet.
- A wallet: their own browser wallet (for example MetaMask) or the one the page makes in the browser. It should be
  the same wallet they claim with.
- Nothing else: no gas, no WBT, no fee, no sign-up, no documents.

### What happens
1. The user opens the link and picks a wallet.
2. The page shows a QR code. It is valid for 10 minutes and refreshes on its own.
3. The user scans it with the phone and taps the card.
4. The page shows "Verified" with the stamp's expiry. From then on, your isStamped check passes for that wallet.
- The same card with the same wallet again renews the stamp.
- The same card with a different wallet in the same app is refused: one card, one wallet per app.

### The Genesis Drop and the bot test
https://usewatermark.xyz/pass is our own drop, built on the same check. It shows the whole flow from a user's side:
1. Verify with your card (/verify?next=pass): a stamp in the live app.
2. Send one free test payment (/pay?next=pass): gas-free USDT through WatermarkSponsor. We pay the fee.
3. Claim the NFT (POST /pass): WatermarkGenesisPass, 100 in total, one per bank card, minted gas-free.
The contract checks the stamp itself. Step 2 is checked by our relayer from the sponsor's PaymentRelayed events,
because a contract can't read past events. https://usewatermark.xyz/attack makes 5 throwaway bot wallets and sends
them at the drop's free perks (USDT funding, a gas-free payment, the pass). Every request is real; every one is refused.

## 9. Sponsoring user fees (WatermarkSponsor)

Stamped wallets can pay in USDT without holding gas or WBT. The business pays the gas through its relayer.

How it works
1. The user signs an EIP-3009 TransferWithAuthorization for USDT: { from, to, value, validAfter, validBefore, nonce }.
   EIP-712 domain: name "Tether USD", version "1", chainId 1874, verifyingContract
   0xcedfB56113143d55b2358b8CFbB0dEB5Ad2f55a7. No transaction, no gas.
2. The relayer calls WatermarkSponsor.relayPayment(intent, signature) and pays the gas.
3. The contract checks that the caller is its relayer, that `from` has a live stamp for its appId, and that `from`
   has sponsored payments left today. Then it submits the authorization to USDT.

Rules in the contract (not on our server)
- One WatermarkSponsor per app. Its appId and relayer are fixed at deploy.
- quotaPerDay = 20: each stamped wallet gets 20 sponsored payments per UTC day. A reverted payment uses no quota.
- Unstamped wallets and wallets over quota are refused on-chain, so even our relayer can't sponsor them.
- Views: quotaLeft(wallet), usedToday(wallet). Event: PaymentRelayed.

Live: the sponsor for the live app is 0x21b6ae18a412afb84a09263939c5e787d374939a. A real gas-free payment under it
(1 USDT to the shop; the payer paid 0):
https://explorer.testnet.whitechain.io/tx/0xb848b7c8c589335d17ab1570f0cb1765325a1d065e58a2f9447e9d333e376879

Relayer-side drain limits (defaults): every payment is simulated before any gas is spent; a per-transaction gas cap
(300,000 for payments) and a daily gas budget, separate from stamps; a per-IP rate limit; and at most 2 mined
reverted payments per wallet per UTC day.

Your own sponsor
- Deploy contracts/script/DeploySponsor.s.sol with your APP_ID, RELAYER_ADDRESS (your relayer's hot wallet) and
  QUOTA_PER_DAY, then run the relayer with SPONSOR_ADDRESS set. Rotating the relayer means a new sponsor.

Known trade-off: a signed EIP-3009 authorization is a bearer instrument. Anyone who sees it can submit it to USDT
directly. That only moves the payer's own USDT to the recipient they signed for, and it skips the quota.

Ethereum alt mempool (EIP-8141 devnet): WatermarkQuotaPaymaster pays for up to 20 frame transactions per UTC day for
each stamped wallet. Its VERIFY frame reads the registry's stamp expiry and its own clock slot, so it stakes itself
(0.012 ETH) to be allowed to read that storage. The daily quota is an EIP-8250 keyed nonce, and the fees are pinned.
One sponsored frame tx was admitted and mined (section 3). Design and trade-offs: docs/EF_ALTMEMPOOL.md.

## 10. Card list (policies)

### What counts in the live app
- 4,208 six-digit card prefixes (BINs): RuPay network, bank debit cards, issued in India.
- Prepaid ranges are left out (gift, transit and payroll cards, which anyone can buy over the counter), and so are
  ranges the dataset gives no category.
- Source: https://github.com/mostafa19950/bin-list-data (CC BY 4.0). It is unofficial and possibly outdated, so every
  leaf is marked "listed", not "tested". No prefix was chosen because of a team member's card.
- What is proven cryptographically: the card network, through the RuPay CA key 05 that signed the card. Bank, card
  type and country are only as good as the BIN list behind the prefixes.
- Full list: policies/live.json in the repo, or GET https://prover.usewatermark.xyz/policy/<appId>.

### How a filter works
- Each leaf is { networkId (1 = RuPay, 2 = Visa, 3 = Mastercard), prefixLength (6 or 8), prefix }.
- rulesRoot is the Poseidon2 Merkle root of the leaves (tree depth 13, up to 8,192 leaves). The circuit proves the
  card's prefix is one of the leaves; the registry checks the proof against apps(appId).rulesRoot.
- Rules are fixed per appId: a new filter means a new appId.
- A narrower filter makes each stamp reveal more. A stamp in an "SBI only" app shows the wallet holds an SBI card.

### Audit any app's filter
1. Read apps(appId) on the registry: owner, rulesRoot, sessionSigner (explorer, SDK appInfo, or the MCP tool
   watermark_app_info).
2. Get the published leaves: policies/<name>.json in the repo, or GET /policy/<appId> on the prover.
3. Recompute the root from the leaves: `node tools/zk/src/roots.ts --check` (CI runs it on every push). The MCP tool
   watermark_app_info and the SDK's auditApp do the comparison for you.
4. Check caRoot() on the registry against policies/ca-keys.json (the trusted network keys).
5. See how many wallets an app has stamped: watermark_stamp_history or the SDK's stampHistory.

### Your own app, with your own card list
1. Draft the filter with watermark_draft_policy (BIN prefixes from a public BIN list). It returns leaves, rulesRoot,
   warnings.
2. Publish the policy (its leaves) where users can see it, so anyone can check your on-chain root against it.
3. Register: watermark_prepare_register_app returns an unsigned registerApp(salt, rulesRoot, sessionSigner)
   transaction and the appId it will create. Sign and send it from the owner wallet.
4. Run a session signer: it signs the QR sessions for your app (our relayer does this for the live app). It decides
   who can start a verification; it can't stamp anyone without a real card and a valid proof.
5. Gate on your new appId (sections 4 to 6). Only RuPay cards can be proven today, whatever the filter says.

## 11. Privacy

What we see and store
- Our prover sees the card data (card number, BIN, card key, certificates, card expiry) briefly, in memory, to make
  the proof. Then it wipes it. You have to trust that wipe; we can't prove it. Proving on the phone is the real fix,
  and it is on the roadmap. Anyone can run their own prover.
- On the network, card data travels only as ciphertext, readable with the prover's key.
- The relayer and the prover see IP addresses and timing. Request logs are off in demo mode.
- What we store: nothing from the card. No KYC files, no documents, no card numbers.

What goes on-chain (public, permanent)
- The wallet, the appId, a nullifier (a one-way card id per app), the stamp's expiry month, and the proof.
- The app's filter (its rulesRoot and its public list).
- USDT payments, like any token transfer.
- Never: the card number, the BIN or the card's expiry.

Rules every part follows
- Never log request bodies, card fields, witnesses or private proof inputs.
- No analytics, trackers or crash reporting anywhere in the flow.
- If you integrate Watermark, you never need card data: your code only sees a wallet address and a yes/no stamp.
- Using one wallet in two apps links them, even though the nullifiers differ.

## 12. Limits

- Only RuPay debit cards work today (cards using the RuPay CA key 05 with the 1984/1408/768-bit, exponent-3 key
  profile). Visa and Mastercard are planned, not live: their filters can be drafted, but no card can be proven yet.
  Each needs its own circuit profile, which plugs into the VerifierRouter without a redeploy.
- Test networks only (Whitechain Sepolia and the alt mempool devnet). A real launch needs PCI and legal review,
  network and bank terms, and a licensed BIN source.
- One card is not one person. Two cards make two stamps. A reissued card has a new key, so it gets a new stamp.
- Possession only: a contactless tap has no PIN, so a borrowed or stolen card also passes.
- No revoke. A stamp lasts until the end of a month 1 to 3 months ahead (our relayer uses 3), never past the card's
  own certificate expiry, and can't be revoked early. A lost wallet can't move its stamp to a new wallet.
- Our prover sees card data briefly, in memory (section 11).
- The nullifier isn't fully secret: anyone who has read the card and knows the appId can compute it and link the
  card to the wallet.
- The chip's challenge is only 4 bytes, so sessions are rate-limited and the relayer chooses the nonce.
- An app's session signer could refuse a user or open too many sessions. It can't stamp anyone without a real card.
- The live list comes from an unofficial BIN dataset that may be out of date.
- Watermark Tap is not in an app store yet, and @watermark/sdk is not on npm yet.

## 13. Example: gate an airdrop end to end

Goal: only wallets backed by a real bank card can claim, one claim each, and unverified users get a clear way in.

Step 1. Choose the appId
Use the live app id (section 3) for real RuPay cards. Register your own app only for a different card list (section 10).

Step 2a. The contract (if it is on Whitechain Sepolia)
Use the Drop contract from section 4. Deploy it with the registry 0x998934Efa31a6bE75945fDfAa126d3D6401F8Fd6. A wallet
without a live stamp gets "Watermark: no live stamp".

Test that an unstamped wallet is refused (Foundry):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.30;

import {Test} from "forge-std/Test.sol";
import {Drop, IWatermarkRegistry} from "../src/Drop.sol";

/// Test double: a wallet is stamped until the expiry you set.
contract MockRegistry is IWatermarkRegistry {
    mapping(address => uint64) public expiry;
    function setExpiry(address wallet, uint64 expiresAt) external {
        expiry[wallet] = expiresAt;
    }
    function isStamped(address wallet, uint256) external view returns (bool ok, uint64 expiresAt) {
        expiresAt = expiry[wallet];
        ok = expiresAt > block.timestamp;
    }
}

contract DropTest is Test {
    MockRegistry registry = new MockRegistry();
    Drop drop = new Drop(registry);
    address bot = address(0xB07);

    function test_unstampedWalletIsRefused() public {
        vm.prank(bot);
        vm.expectRevert(bytes("Watermark: no live stamp"));
        drop.claim();
    }
}
```
(To test the happy path, call registry.setExpiry(wallet, uint64(block.timestamp + 30 days)) first.)

Step 2b. The backend (if the contract is on another chain, or the payout is off-chain)
Check on the server, right before you pay out or add the wallet to the allowlist:

```ts
import { check, type CheckOptions } from "@watermark/sdk";

const REGISTRY = "0x998934Efa31a6bE75945fDfAa126d3D6401F8Fd6";
const APP_ID = "393344891601835728760966937624776276735512086066329273346256164761263100630";

export async function assertStamped(wallet: string, opts: CheckOptions = {}): Promise<void> {
  const { stamped } = await check(wallet, APP_ID, { registry: REGISTRY, ...opts });
  if (!stamped) throw new Error(`NOT_STAMPED: verify at https://usewatermark.xyz/verify?app=${APP_ID}`);
}
```

Test that an unstamped wallet is refused (node --test; `client` replaces the chain read):

```ts
import { test } from "node:test";
import assert from "node:assert/strict";
import { assertStamped } from "./watermark-gate.ts"; // the file above

test("an unstamped wallet is refused", async () => {
  const client = { readContract: async () => [false, 0n] as const };
  await assert.rejects(assertStamped("0x000000000000000000000000000000000000dEaD", { client }), /NOT_STAMPED/);
});
```

For a snapshot allowlist, run checkMany over your claim list in batches of 200 and keep the stamped wallets. Check
again with check() at claim time, because stamps expire.

Step 3. The way in for unverified users
When the claim is refused, show a "Get verified with Watermark" button that opens
https://usewatermark.xyz/verify?app=<APP_ID>. Ask the user to choose the wallet they claim with. When they come back,
check again (check(), isStamped, or GET /status/:wallet?app=<APP_ID>&chain=1874) and enable the claim.

Step 4. Don't touch card data, and watch it work
Your app never asks for, stores or logs card numbers or any card field. It only needs the wallet address.
watermark_stamp_history (MCP) or stampHistory (SDK) shows how many wallets your appId has stamped and which are live.

## 15. Customize it

What a business can change, how, and what runs today. "On-chain" means the contracts enforce it, not our servers.
The same table, for people: https://usewatermark.xyz/docs#customize

Stamp length
- Options: 1, 2 or 3 months. A stamp lasts until the end of a month 1 to 3 months ahead (on-chain rule: the registry
  refuses any other validUntilMonth). A renewal only ever extends a stamp, never shortens it.
- How: the app's session signer picks the month when it signs each session. Our relayer uses 3 months for the live
  and test apps. Your own app with your own session signer can choose 1 or 2.
- Shorter windows, such as "tapped in the last hour / 24 hours / 7 days": isStamped only gives the expiry, not when
  the card was tapped. Your backend reads the stamp's time instead: stampHistory (SDK) or the registry's Stamped
  event gives each stamp's block (a renewal emits a new event); read that block's timestamp and decide. A contract
  can't read past events, so do this off-chain.
- Longer than 3 months: not possible today. The 3-month cap is in the registry, so it needs a registry upgrade.

Claims per wallet per day
- Airdrops, mints and rewards: your own contract decides (1, 5, 20 or any number). The Drop example in section 4 keeps
  one claim per wallet with a `claimed` mapping.
- Sponsored payments: each WatermarkSponsor has its own quotaPerDay per wallet per UTC day, fixed when it is deployed
  (QUOTA_PER_DAY in contracts/script/DeploySponsor.s.sol). Ours is 20.

Which cards count
- Your own card list: BIN prefixes (6 or 8 digits, up to 8,192) from a public BIN list. For example leave out prepaid,
  or keep only some banks' listed ranges. The live app's list: 4,208 RuPay bank-debit ranges, no prepaid.
- How: draft it with watermark_draft_policy (SDK draftPolicy), then register your own app with
  watermark_prepare_register_app (SDK prepareRegisterApp) and send that unsigned transaction from your wallet
  (section 10). Your own app runs its own session signer.
- A list can't change after you register it: a new list means a new appId.

One card, one wallet per app
- Always on (on-chain). The registry binds each card's nullifier to one wallet per app.
- A new campaign where the same cards may join again can use a new appId.

Who pays network fees
- You do, so your users pay $0. Stamps: the relayer pays the gas. Payments: deploy your own WatermarkSponsor
  (DeploySponsor.s.sol with APP_ID, RELAYER_ADDRESS and QUOTA_PER_DAY) and run the relayer with SPONSOR_ADDRESS
  (section 9).
- Caps: PAY_MAX_USDT (largest payment, default 5 USDT), MAX_GAS_PER_PAY (gas per payment, default 300,000) and
  DAILY_BUDGET_WEI (payment gas per UTC day, default 0.1 WBT).

Rate limits and budgets (relayer environment settings, relayer/src/config.ts; defaults in brackets)
- SESSIONS_PER_MINUTE_PER_IP (10), MAX_OPEN_SESSIONS (5000)
- STAMPS_PER_MINUTE_PER_IP (30), STAMP_MAX_QUEUE (20), MAX_GAS_PER_STAMP (3,500,000), STAMP_BUDGET_WEI (0.1 WBT a day)
- PAYS_PER_MINUTE_PER_IP (10), MAX_GAS_PER_PAY (300,000), DAILY_BUDGET_WEI (0.1 WBT a day), PAY_MAX_USDT (5),
  PAY_MAX_REVERTS_PER_WALLET (2), PAY_PAUSED (false)
- PASSES_PER_MINUTE_PER_IP (5), MAX_GAS_PER_PASS (500,000), PASS_BUDGET_WEI (0.1 WBT a day): the Genesis Pass only
- CORS_ORIGINS: the websites allowed to call the relayer from a browser

Card networks
- RuPay debit: live. Visa and Mastercard: planned, not live. Their card lists can be drafted, but no card can be proven
  yet.

Chains
- Whitechain Sepolia (1874): live. Contracts there check the stamp directly.
- Any other chain: check from your backend before you pay out (section 5). Running the registry on another chain means
  deploying it there; our relayer only serves Whitechain Sepolia and the alt mempool devnet today.

Pricing: free during the hackathon testnet.
